## Hypothesis
Given:
An engineering team facing an architecture decision

And:
Explicit context: team size, budget, deadline, performance need,
team familiarity with each option, operational tolerance

And:
Two or more named alternatives, each with known characteristics

The system should:
Evaluate each alternative against each constraint,
surface trade-offs the team may not have made explicit,
produce a ranked recommendation with a transparent reasoning trace,
and expose where uncertainty exists

Because:
The value is not in replacing the decision —
it is in making the reasoning visible before commitment

Success would mean:
A team can input a real decision scenario,
receive a recommendation they find credible,
see the trade-offs they are accepting,
and have the option to adjust their constraints and re-evaluate

## Smallest Testable System

The question was: what is the smallest thing that can prove or
disprove this hypothesis?

Answer:

A TypeScript script that:
1. Accepts a structured decision scenario as input
2. Evaluates each option against each constraint
3. Scores each option
4. Produces a recommendation
5. Exposes the reasoning — which constraints each option satisfies,
   which it fails, and what trade-off is being accepted

No database. No API. No UI framework. No AI model dependency.
The reasoning engine itself is the experiment.

## Decision Pipeline
Decision Input (scenario)
│
▼
Context Builder
Extracts: constraints, weights, options
│
▼
Constraint Evaluator
For each option × each constraint:
- does this option satisfy this constraint?
- to what degree? (pass / partial / fail)
│
▼
Scorer
Weighted score per option
Score reflects constraint satisfaction, not preference
│
▼
Trade-off Analyser
Identifies: which constraints are sacrificed by the
top-ranked option vs the second-ranked option
│
▼
Recommendation
Primary: highest scoring option
With: explicit reasoning trace
With: trade-offs named
With: uncertainty flagged where constraints are partial
│
▼
Human Decision
Team reviews, may override, proceeds with awareness

## Component Definitions

### Decision Input
A structured object containing:
- The decision being made (description)
- Available options (array of named alternatives)
- Active constraints (array of named constraints with weights)
- Context values (team size, budget, deadline, etc.)

### Context Builder
Reads the input. Validates that options and constraints are present.
Prepares the evaluation matrix.

### Constraint Evaluator
For each (option, constraint) pair:
- Evaluates satisfaction: PASS (1.0), PARTIAL (0.5), FAIL (0.0)
- Uses option-specific capability data to determine this

### Scorer
Weighted sum across constraints per option.
Weight reflects how critical each constraint is to this decision.
A constraint weighted 5 matters more than one weighted 1.

### Trade-off Analyser
Compares top two options.
Identifies: what does option A satisfy that option B does not?
What does option B satisfy that option A does not?
This surfaces the actual trade-off, not a generic summary.

### Recommendation
Outputs:
- Recommended option (highest weighted score)
- Score breakdown per option
- Trade-off statement
- Confidence level (HIGH / MEDIUM / LOW based on score margin)
- Any constraints marked as uncertain

## Evaluation Criteria

The prototype succeeds if:

1. It accepts a real-world architecture scenario as input
2. It produces a recommendation that a reasonable engineer
   would find plausible
3. The recommendation is explained — the reasoning is visible
4. It correctly identifies the trade-off being made
5. It runs without errors on at least three different scenarios
6. The output is honest — it flags uncertainty where it exists

The prototype fails if:

1. It always recommends the same option regardless of input
2. Its reasoning cannot be followed by a reader
3. It crashes on a valid input
4. It produces a confident recommendation when constraints
   are contradictory
