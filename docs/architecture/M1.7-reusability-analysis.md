## 2. Component Reusability Map

| Component              | Scenario A Specific? | Reusable? | Why |
| ---------------------- | -------------------- | --------- | --- |
| Input parser           | No                   | Yes       | `run-json.ts` reads any valid `DecisionScenario` JSON. Zero domain assumptions. |
| Context builder        | No                   | Yes       | `context` field is `Record<string, string \| number>`. Accepts arbitrary key-value pairs. Engine ignores it (informational only). |
| Decision model         | No                   | Yes       | `evaluate()` operates on constraints, weights, and satisfaction levels. No domain logic. |
| Constraint handling    | No                   | Yes       | Constraints are data, not code. Any domain can define any constraints with any weights 1-5. |
| Reasoning engine       | No                   | Yes       | `evaluateOption()`, `analyseTradeOff()`, `calculateConfidence()` are pure math. Domain-agnostic. |
| Alternative comparison | No                   | Yes       | `analyseTradeOff()` compares top two ranked options by satisfaction scores. Works for any option type. |
| Recommendation         | No                   | Yes       | Ranking by weighted score is universal. Confidence thresholds (20%, 8%) are configurable in principle. |
| Explanation generator  | No                   | Yes       | `buildReasoning()` constructs natural language from score data. No domain vocabulary hardcoded. |

**Conclusion:** Every component is reusable. The engine contains zero domain-specific logic. The scenario is entirely data.

## 4. Architecture Observations

1. **The engine is a pure function.** `evaluate(scenario: DecisionScenario): Recommendation` has no side effects, no state, no external dependencies. This is the strongest possible foundation for reusability.

2. **The `context` field is currently informational.** The engine does not use it for reasoning. It exists in the type but is not consumed by `evaluate()`. This is honest — the engine evaluates constraints, not context. Context is for the human reader.

3. **Satisfaction levels are pre-assigned.** The engine does not determine whether an option passes or fails a constraint — the scenario author does. The engine's job is aggregation, ranking, and trade-off surfacing. This is a deliberate design choice, not a limitation.

4. **The text-wrap bug from M1.4 is fixed in `run-json.ts`.** The new runner uses word-boundary-aware wrapping instead of the fixed-character regex. The original `run.ts` retains the old behaviour (unchanged, per M1.7 scope).

---

## 5. Generalisation Assessment

The same core engine — completely unmodified — processed two meaningfully different decision scenarios:

- **Scenario A:** Technical architecture (3 options, 6 constraints, infrastructure domain)
- **Scenario B:** Hiring decision (3 candidates, 6 constraints, people/HR domain)

Both produced credible, nuanced outputs with correct trade-off identification. The engine does not know what "hiring" or "architecture" means. It evaluates weighted constraints against satisfaction levels. The domain is entirely in the data.

**Verdict: The Decision Intelligence prototype is a reusable capability, not a one-off demo.**
