## What the Prototype Did

Scenario: a 4-person engineering team choosing between three backend
architecture options for an internal analytics service.

Constraints active:
- Infrastructure budget ≤ $200/month          (weight 4)
- Team capability — no new learning curve      (weight 5)
- Deliverable within 3 weeks                   (weight 5)
- p95 response time < 200ms                   (weight 3)
- Operable without dedicated DevOps            (weight 4)
- No hard vendor lock-in                       (weight 2)

Options evaluated:
- Option A — Monolith (Next.js API Routes)
- Option B — Separate Node.js Service (Fastify)
- Option C — Serverless Functions (AWS Lambda)

## Actual Output

### Ranked scores

| Option                          | Score | Weighted     |
| ------------------------------- | ----: | -----------: |
| A — Monolith (Next.js API)      |   89% | 20.5 / 23    |
| B — Node.js Service (Fastify)   |   61% | 14.0 / 23    |
| C — Serverless (AWS Lambda)     |   24% |  5.5 / 23    |

### Recommendation

Option A — Monolith (Next.js API Routes)
Confidence: HIGH

### Trade-off surfaced

Choosing A over B means accepting weaker performance on:
- p95 response time (PARTIAL vs PASS in B)
- vendor lock-in (PARTIAL vs PASS in B)

In return, A performs better on:
- budget (PASS vs PARTIAL)
- team capability (PASS vs PARTIAL)
- delivery speed (PASS vs PARTIAL)
- operational complexity (PASS vs PARTIAL)

### Uncertain constraints flagged

- p95 Response Time < 200ms: cold start risk on Vercel Functions
- No Hard Vendor Lock-in: Vercel dependency acknowledged but manageable

## What Worked

### 1. The engine ran without errors on a real scenario

The pipeline executed end to end:
Input → Evaluate → Score → Rank → Trade-off → Recommend → Explain

This proves the hypothesis is mechanically sound.

### 2. The recommendation was credible

Option A is the correct answer for this scenario by conventional
engineering judgement. A senior engineer reviewing this output would
agree with the recommendation and the reasoning.

The engine did not produce a random or arbitrary result.

### 3. Trade-offs were correctly identified

The engine correctly identified that choosing A over B means accepting
worse performance headroom and slightly more vendor dependency.

This is exactly the trade-off a real team would need to understand.
The engine surfaced it without being asked.

### 4. Uncertainty was honest

The engine flagged two PARTIAL constraints rather than rounding them
to PASS. It named the specific risks rather than hiding them in a
confident recommendation.

### 5. Constraint weighting changed the result

Option C had the cheapest infrastructure cost (PASS on budget).
But its failures on high-weight constraints (team capability w:5,
delivery speed w:5, operational complexity w:4) correctly drove it
to last place.

The weighting system functioned as designed.

### 6. No external dependencies were required

The engine is deterministic pure TypeScript.
No AI model. No API call. No database.
The reasoning is entirely transparent and reproducible.

## What Failed

### 1. Text wrapping in the output is imperfect

The runner wraps output at 70 characters with a fixed regex split.
This causes mid-word breaks in some constraint notes.
Adequate at current scale. Cold starts on Vercel Functions may cause p
95 spikes under initial load.

text


The `p` at end of line and `95` at start of next is a formatting bug.
This does not affect the reasoning — only the readability of the report.

### 2. The scenario data is static

The scenario is defined as a TypeScript object.
A real system would accept dynamic input — a form, a CLI prompt,
or a structured file.

The current prototype cannot be used by someone who does not
know how to write TypeScript.

### 3. One scenario was tested

The engine was run against one scenario.
A single successful run does not prove the engine generalises.
It proves it works for this input.

## What Surprised Us

### Constraint weighting matters more than option quality

Option C passed the budget constraint that Options A and B only
partially passed. In a naive comparison, C would appear competitive
on cost. The weighting system correctly deprioritised this because
the team capability and delivery constraints were weighted higher.

This is non-obvious. A decision-maker looking only at a pros/cons
list might have rated C as viable. The engine correctly ranked it
last by a significant margin (24% vs 89%).

This is the core value proposition: **weight reveals priority.**

### The trade-off output is more valuable than the recommendation

The recommendation (Option A) was predictable once the weights were
set. What was not predictable was the precise articulation of what
is being sacrificed.

The statement:
> "Choosing A over B means accepting weaker performance on p95
> response time and vendor lock-in. In return it performs better
> on budget, team capability, delivery speed, and operations."

is more useful than:
> "Choose A."

This suggests the trade-off surface is where the most product
value lives, not the recommendation itself.

---

## What Assumptions Were Wrong

### Assumption: the recommendation would be the interesting part

Before building, the assumption was that users would want a
recommendation. The prototype revealed that the trade-off
analysis is more valuable than the recommendation.

Users likely already have a preferred option.
What they lack is a structured argument for or against it.

### Assumption: more constraints would improve accuracy

The current model treats all constraints as independent.
In reality, constraints interact — a tight deadline may make
team capability even more critical than its weight suggests.

The current engine does not model constraint interaction.
This is a real limitation.

## Limitations

1. **Input is code.** The scenario must be written as TypeScript.
   This limits users to developers.

2. **Single scenario tested.** Generalisation is unproven.

3. **Static capability data.** Option capabilities are manually
   defined. A real system would need a way to derive or input
   these from context.

4. **No constraint interaction.** Constraints are scored
   independently. Real decisions have constraint dependencies.

5. **Output formatting has a known bug.** Mid-word line breaks
   in long constraint notes.

---

## What Should Change Before Production

1. Add a second and third scenario to verify generalisation.
2. Replace the static TypeScript scenario with a structured
   input format (JSON or CLI prompt).
3. Fix the word-wrap bug in the runner.
4. Explore constraint interaction — can two constraints together
   change an evaluation that each would not change alone?
5. Consider whether the trade-off output should be the primary
   interface, with the recommendation secondary.
