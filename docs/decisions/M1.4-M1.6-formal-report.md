## 3. M1.4 — Research and Development

### 3.1 Problem Discovery

The first stage was choosing a concrete decision domain rather than building toward a vague idea.

The domain selected: **engineering architecture decisions under constraint.**

Rationale for selection over alternatives:

| Domain considered | Why rejected or deprioritised |
|---|---|
| Product decisions | Inputs too fuzzy, hard to evaluate objectively |
| Resource allocation | Requires real organisational data |
| Risk decisions | Domain expertise dependency too high for prototype |
| Planning decisions | Too broad, not bounded enough |
| **Architecture decisions** | **Concrete inputs, bounded alternatives, real trade-offs, no external data required** |

Architecture decisions have all the properties a testable system requires: named inputs, enumerable alternatives, explicit constraints, and consequences that are traceable. The problem was documented in full in `docs/architecture/M1.4-problem-definition.md`.

---

### 3.2 Hypothesis

```
Given:
    An engineering team facing an architecture decision

And:
    Explicit context: team size, budget, deadline, performance need,
    team familiarity, operational tolerance

And:
    Two or more named alternatives with known characteristics

The system should:
    Evaluate each alternative against each constraint,
    surface trade-offs the team may not have made explicit,
    produce a ranked recommendation with a transparent reasoning trace,
    and expose where uncertainty exists

Because:
    The value is not in replacing the decision —
    it is in making the reasoning visible before commitment

Success would mean:
    A team inputs a real decision scenario,
    receives a recommendation they find credible,
    sees the trade-offs they are accepting,
    and can adjust constraints and re-evaluate
```

---

### 3.3 Architecture

The smallest system capable of testing the hypothesis was defined as six components:

```
Decision Input (structured scenario)
        │
        ▼
Context Builder
    Validates and prepares the evaluation matrix
        │
        ▼
Constraint Evaluator
    For each (option × constraint): PASS / PARTIAL / FAIL
        │
        ▼
Scorer
    Weighted sum per option
        │
        ▼
Trade-off Analyser
    Compares top two options
    Names what is sacrificed by the recommended choice
        │
        ▼
Recommendation
    Ranked options + trade-off statement + uncertainty flags
    + reasoning trace + confidence level
        │
        ▼
Human Decision
    Team reviews, may override, proceeds with awareness
```

Technology decision: TypeScript, no external dependencies, no AI model, no database, no API. Rationale: the reasoning engine itself is the experiment. Infrastructure would obscure whether the hypothesis is sound.

Full architecture: `docs/architecture/M1.4-decision-intelligence-architecture.md`

### 3.4 Prototype

Three files were created under `research/decision-intelligence/prototype/` — explicitly separated from the production codebase:

#### `engine.ts`
The core reasoning engine. Implements:
- Type definitions for scenarios, constraints, options, scores, trade-offs
- `evaluateOption()` — scores one option against all constraints
- `analyseTradeOff()` — compares top two ranked options, names wins and losses
- `calculateConfidence()` — HIGH / MEDIUM / LOW based on score margin between top two
- `findUncertainConstraints()` — surfaces all PARTIAL satisfactions explicitly
- `buildReasoning()` — constructs a human-readable reasoning statement
- `evaluate()` — the public entry point; accepts a scenario, returns a full recommendation

Pure TypeScript. Zero external imports.

#### `scenarios/architecture-choice.ts`
A real decision scenario:

```
Team:        4 engineers, no dedicated DevOps
Budget:      ≤ $200/month
Deadline:    3 weeks
Performance: p95 < 200ms

Options:
  A — Monolith (Next.js API Routes)
  B — Separate Node.js Service (Fastify)
  C — Serverless Functions (AWS Lambda)

Constraints (weighted):
  Infrastructure Budget ≤ $200/month         w:4
  Team capability — no new learning curve     w:5
  Deliverable within 3 weeks                  w:5
  p95 Response Time < 200ms                  w:3
  Operable without dedicated DevOps           w:4
  No hard vendor lock-in                      w:2
```

Each option's capability against each constraint was defined with satisfaction level and an explicit note explaining the assessment.

#### `run.ts`
Executes the engine against the scenario and formats the output as a human-readable report.

### 3.6 Findings

The full findings document is at `docs/decisions/M1.4-rnd-findings.md`. Key findings summarised here.

#### What worked

**The recommendation was credible.** Option A is the correct answer for this scenario by conventional engineering judgement. A senior engineer reviewing the output would agree with the recommendation and the reasoning trace.

**Trade-offs were correctly identified.** The engine named precisely what was being sacrificed (performance headroom, lower vendor dependency) and what was being gained (team velocity, operational simplicity, budget fit) without being asked to find them.

**Constraint weighting changed the result in a meaningful way.** Option C had the cheapest infrastructure (PASS on budget). A naive comparison might have rated it competitive. The weighting system correctly drove it to last place because its failures on team capability (w:5) and delivery speed (w:5) dominated the evaluation. This is the core mechanism.

**Uncertainty was honest.** Two constraints were flagged as PARTIAL rather than rounded to PASS. The engine named the specific risks rather than absorbing them into a confident output.

**No external dependencies were required.** The reasoning is deterministic, transparent, and fully reproducible. Anyone reading `engine.ts` can follow every calculation.

#### What failed

**Text wrapping has a formatting bug.** The runner wraps at 70 characters using a fixed regex, which causes mid-word breaks on long constraint notes. This does not affect reasoning — only readability of the printed report.

**Input requires TypeScript.** Scenarios are TypeScript objects. A non-developer cannot currently use the prototype without assistance.

**Only one scenario was tested.** A single successful run proves the engine works for this input. It does not prove generalisation.

#### What surprised us

**The trade-off output is more valuable than the recommendation.**

The recommendation (Option A) was predictable once the weights were set. What was not predictable was the precise articulation of what is being sacrificed. The statement:

> *"Choosing A over B means accepting weaker p95 performance and slightly more vendor dependency. In return it performs better on budget, team capability, delivery speed, and operational complexity."*

is substantially more useful than:

> *"Choose A."*

This finding suggests the trade-off surface — not the recommendation — is where the most product value lives. This reorients what the next iteration should emphasise.

**Constraint interaction is the next real problem.** The engine currently scores constraints independently. In reality they interact — a tight deadline may make team capability even more critical than its weight alone suggests. The current model does not capture this. It is the most significant architectural limitation identified.

This section is the most important part of the contract. It draws a hard line between what can be said publicly and what cannot.

Demonstrated on: backend architecture decision under six constraints. Produces: ranked options, trade-off statement, uncertainty flags, reasoning trace.

**Experimental — currently being built:**

```

Dynamic input (non-TypeScript scenarios)
Multiple scenario domains beyond architecture choice
Collaborative / multi-user decision support
```

**Future — plausible but not implemented:**

```
Integration with engineering tools (ADRs, Linear, Jira)
Decision history and traceability
Pattern recognition across repeated decisions
Team-calibrated constraint weighting
```

**Explicitly not claimable:**

```
✗ "AI-powered decision intelligence"
✗ "Makes better decisions for you"
✗ "Decisions at scale"
✗ "General-purpose decision platform"
✗ "Replaces human judgement"
✗ "Learns from your decisions"
✗ "Integrates with your tools"
```

None of these are currently true. None may appear in public copy.

## 9. Recommended Next Steps

These are sequenced by dependency. Each step has a clear entry condition.

**Step 1 — Second scenario validation**
Write and execute a second scenario from a different decision domain — e.g. a product decision or a hiring decision. If the engine produces a credible output, generalisation is partially supported and the v0.1.0 input gate is within reach.

**Step 2 — Dynamic input mechanism**
Replace the TypeScript scenario object with a structured input format — JSON file, CLI prompt, or minimal web form. This is the prerequisite for a non-developer being able to use the prototype and for the public page to be honest about accessibility.

**Step 3 — Fix word-wrap in runner**
Minor. Replace the fixed-character regex wrap with a word-boundary-aware implementation.

**Step 4 — Public page implementation**
After steps 1 and 2 are complete, implement `/decision-intelligence` against the contract defined in `M1.6-branch-contract.md`. Every claim on the page must be defensible against the prototype output. No claim from the future or experimental sections may appear without a flag.

**Step 5 — Constraint interaction research**
Investigate whether modelling constraint dependencies produces materially better recommendations. This is the v0.2.0 gate and should not block v0.1.0.

## 10. Assessment of the Milestone

### What this milestone set out to do

> Determine whether Decision Intelligence deserves to become Aryntra's first public branch.

### What it found

It deserves it. Not because the idea is attractive — it was always attractive, which is why it scored 5/5 on strategic fit at M1.3. It deserves it because there is now something real: a working engine that produces a credible, trade-off-aware, uncertainty-honest recommendation from structured input.

The most important discovery was not the recommendation mechanism. It was the finding that **the trade-off surface is more valuable than the recommendation itself.** This reorients the product direction. Users likely already have a preferred option. What they lack is a structured argument that names what they are accepting and what they are sacrificing. That is what the engine produces — and that is what no current tool produces.

### What it did not find

It did not find a finished product. It found a validated prototype in a single scenario. Generalisation is unproven. Input accessibility is limited. These are known gaps with a clear path to resolution.

### What it protected

The production codebase is in exactly the state it was at the start of M1.4. Six commits, zero changes to `apps/web/`. The v0.0.0 trunk is preserved.
