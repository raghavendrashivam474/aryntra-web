## 4. Phase 1 — Scenario A Reproduction & Reusability Analysis

### 4.1 Engine Inspection

Before creating Scenario B, the existing engine was inspected to understand the input contract.

The `DecisionScenario` type is:

```typescript
interface DecisionScenario {
  id: string;
  description: string;
  context: Record<string, string | number>;
  constraints: Constraint[];    // id, label, weight (1-5), description
  options: Option[];            // id, label, capabilities[]
}
```

Key observations:

- **All fields are JSON-serializable.** No functions, no classes, no non-serializable types.
- **The `context` field is informational.** The engine does not consume it for reasoning. It exists for human readability.
- **Satisfaction levels are pre-assigned by the scenario author.** The engine aggregates; it does not determine PASS/PARTIAL/FAIL. This is a deliberate design choice.
- **The `evaluate()` function is pure.** No side effects, no state, no external dependencies. Input → output.

### 4.2 Reusability Map

Every component was evaluated for domain specificity:

| Component | Scenario-Specific? | Reusable? |
|---|---|---|
| Input parser | No | Yes — reads any valid DecisionScenario |
| Context builder | No | Yes — accepts arbitrary key-value pairs |
| Constraint evaluator | No | Yes — operates on abstract constraint data |
| Scorer | No | Yes — weighted sum is domain-agnostic |
| Trade-off analyser | No | Yes — compares satisfaction scores, not domain content |
| Confidence calculator | No | Yes — margin-based thresholds |
| Reasoning builder | No | Yes — constructs text from score data |

**Conclusion: zero domain-specific logic exists in the engine.**

Full analysis: `docs/architecture/M1.7-reusability-analysis.md`

## 5. Phase 2 — Scenario B Design

### 5.1 Domain Selection

Scenario B needed to be **meaningfully different** from Scenario A. The M1.4 formal report suggested hiring or product decisions as alternatives.

| Dimension | Scenario A | Scenario B |
|---|---|---|
| Domain | Technical infrastructure | People / Human Resources |
| Options | Software architectures | Human candidates |
| Constraint types | Budget, performance, ops | Salary, availability, culture |
| Evaluation basis | System capabilities | Human qualifications |
| Decision maker | Engineering team | Hiring manager |

Hiring was selected because:
- The constraint types are structurally different (salary, culture fit, start date vs. p95 latency, vendor lock-in)
- The options represent people, not systems
- The trade-offs are qualitatively different (domain expertise vs. budget vs. availability)
- A credible output would be immediately recognisable to any hiring manager

### 5.2 Scenario B Definition

**Decision:** Hire a senior backend engineer for a 12-person Series A startup. Must ship core API rewrite within 2 months. Budget capped at $160k base.

**Options:**
- **Candidate A** — Senior Go Engineer at Stripe (7 YOE). Deep technical and domain expertise, but over budget ($185k+ expected) and uncertain cultural fit.
- **Candidate B** — Backend Lead at Series B Startup (5 YOE). Strong across all critical constraints, within budget ($155k), available in 3 weeks. Only gap: no direct fintech experience.
- **Candidate C** — Staff Engineer at Big Tech (10 YOE). Most experienced, but over budget ($180k+), unavailable for 9 weeks, culturally mismatched.

**Constraints (6, weighted 2-5):** Technical depth (w:5), leadership (w:4), salary budget (w:4), start date (w:5), cultural fit (w:3), domain knowledge (w:2).

Full definition: `docs/decisions/M1.7-scenario-b.md`

## 6. Phase 3 — External Input Mechanism

### 6.1 Design Decision

The M1.6 contract required "input mechanism beyond TypeScript objects." The simplest appropriate mechanism was selected: **JSON file input via CLI argument.**

Rationale for JSON over alternatives:

| Mechanism | Considered? | Why / Why Not |
|---|---|---|
| JSON file | **Selected** | Simplest. Proves external input. No infrastructure. |
| CSV | No | Lossy for nested structures (capabilities per option). |
| CLI interactive | No | Unnecessary complexity for validation. |
| HTTP request | No | Requires a server. Overkill for prototype validation. |
| Web form | No | Requires UI work. Out of M1.7 scope. |

### 6.2 Implementation

A new file `run-json.ts` was created alongside the existing `run.ts`. The original runner was **not modified.**

`run-json.ts` provides:
- CLI argument for file path
- UTF-8 JSON file reading
- Schema validation (checks id, description, constraints, options, weights)
- Word-boundary-aware text wrapping (fixes the M1.4 regex wrap bug)
- Same report format as `run.ts` with an additional `[JSON Input Mode — M1.7]` header

Usage:
```
pnpm exec tsx research/decision-intelligence/prototype/run-json.ts <path-to-scenario.json>
```

### 6.3 UTF-8 BOM Issue

During implementation, a platform-specific issue was discovered: PowerShell's `Set-Content -Encoding UTF8` writes a UTF-8 BOM (Byte Order Mark, `\uFEFF`) at the start of files. `JSON.parse()` in Node.js rejects this as invalid JSON.

**Resolution:** JSON files were written using `[System.IO.File]::WriteAllText()` with `UTF8Encoding($false)` (no BOM). This is a tooling concern, not an engine limitation.

## 15. Assessment of the Milestone

### What this milestone set out to do

> Determine whether the Decision Intelligence prototype is a reusable capability or a one-off demo.

### What it found

It is a reusable capability. The same deterministic engine — completely unmodified — evaluated two meaningfully different decision scenarios from different domains and produced credible, nuanced outputs in both cases. The hiring scenario's trade-off analysis (domain expertise vs. budget/availability/culture) is qualitatively different from the architecture scenario's trade-off analysis (performance vs. velocity/ops), yet the engine handled both without any domain-specific programming.

### What it did not find

It did not find a finished product. The input mechanism is JSON files, not a user interface. Constraint interaction is still not modelled. Only two domains have been tested. These are known limitations with clear paths to resolution in future milestones.

### What it protected

The production codebase remains in exactly the state it was at the start of M1.4. The original engine and runner are unmodified. Four commits, zero changes to `apps/web/` or `packages/`. The v0.0.0 trunk is preserved.
